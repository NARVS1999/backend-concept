Phase 3: Caching & Performance — Lesson 2 of 3

Cache Invalidation

"There are only two hard things in computer science: cache invalidation and naming things." — Phil Karlton

Lesson Goal Maunawaan ang iba't ibang strategies para i-invalidate ang stale cache data at maiwasan ang pag-serve ng outdated information.

Bakit Mahirap ang Cache Invalidation?

Kapag may nagbago sa source of truth (database), kailangan ma-reflect ang pagbabago sa cache. Pero hindi agad alam ng cache na may nagbago sa DB — kaya pwedeng mag-serve ang cache ng lumang data.

Invalidation Strategies

1. TTL (Time-To-Live)

  • Set ng expiration time sa cached data
  • Simplest approach — pero pwedeng mag-serve ng stale data hanggang mag-expire ang TTL
  • Dapat i-balance ang TTL: masyadong mahaba = stale data; masyadong maikli = hindi effective ang cache

2. Event-based Invalidation

  • Kapag may nagbago sa DB, mag-send ng event na magti-trigger ng cache invalidation
  • Mas accurate — halos real-time
  • Mas complex — kailangan ng event system

3. Cache Tagging

  • I-tag ang cached data para i-invalidate lahat ng related entries nang sabay-sabay
  • Example: i-tag ang "user:123" at "users:list" — kapag may nagbago sa user, i-invalidate lahat ng may related tags

Mini-Project: Stale Cache Simulation

I-simulate ang stale cache scenario — magpalit ng data sa DB, tignan kung kelan mag-uupdate ang cached response, tapos ayusin gamit ang proper invalidation.

Quiz

Summary

  • TTL: simplest, pero may window ng stale data
  • Event-based: real-time, pero mas complex
  • Cache tagging: i-invalidate related entries nang sabay-sabay
