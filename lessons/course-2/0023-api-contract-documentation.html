API Contract Documentation

Bakit ba kailangang i-document ang API endpoints at paano gawin ito nang simple pero effective?

Lesson Goal Sa lesson na ito, magagawa mong i-document ang lahat ng API endpoints gamit ang mga simple na approaches (markdown docs, Postman collection), i-standardize ang API response format, at malaman kung bakit mahalaga ang API contracts sa team collaboration.

Bakit Kailangan ng API Contract Documentation?

Ang API contract ay ang "agreement" sa pagitan ng backend at frontend — kung ano ang mga available endpoints, paano sila tatawagin, at ano ang responses na aasahan. Kapag walang documentation, nagkakaroon ng mga problema:

Miscommunication: Ang frontend developer ay nag-a-assume ng ibang response format kaysa sa actual na sinasend ng backend. Nagre-result ito ng bugs at wasted time.

Onboarding: Ang bagong team member ay mahihirapan intindihin ang API nang walang documentation. Kailangan nilang basahin ang buong codebase para lang malaman kung paano gumagawa ng isang API call.

Maintenance: Kapag may changes sa API, mahirap malaman kung aling parts ang naapektuhan kung walang documented contract.

Testing: Ang QA team ay hindi makakapag-gawa ng test cases nang tama kung hindi nila alam ang expected inputs at outputs ng bawat endpoint.

Simple API Documentation Approach

Hindi mo kailangan ng complex tools para mag-document. Ang isang markdown file ay sapat na para sa karamihan ng projects. Narito ang format na pwede mong gamitin:

# API Documentation

## Base URL
- Development: http://localhost:8000/api
- Production: https://api.roxy.com/api

## Authentication
Lahat ng authenticated endpoints ay nangangailangan ng
Bearer token sa Authorization header:
```
Authorization: Bearer {token}
```

---

## Products

### GET /products
Get all products.

**Query Parameters:**
- `page` (optional) - Page number, default: 1
- `per_page` (optional) - Items per page, default: 15
- `category` (optional) - Filter by category slug

**Response (200):**
```json
{
  "success": true,
  "data": {
    "data": [...],
    "current_page": 1,
    "last_page": 5,
    "per_page": 15,
    "total": 75
  }
}
```

### GET /products/{id}
Get single product.

**Response (200):**
```json
{
  "success": true,
  "data": {
    "id": 1,
    "name": "Roxy Dress",
    "price": 1299.00,
    "description": "...",
    "category": { "id": 1, "name": "Dresses" },
    "images": [...]
  }
}
```

**Response (404):**
```json
{
  "success": false,
  "message": "Product not found",
  "errors": {}
}
```

### POST /products
Create new product. (Admin only)

**Request Body:**
```json
{
  "name": "New Product",
  "price": 999.00,
  "description": "Product description",
  "category_id": 1
}
```

**Response (201):**
```json
{
  "success": true,
  "message": "Product created",
  "data": { "id": 2, "name": "New Product", ... }
}
```

**Validation Errors (422):**
```json
{
  "success": false,
  "message": "Validation failed",
  "errors": {
    "name": ["The name field is required."],
    "price": ["The price must be a number."]
  }
}
```

Ang format na ito ay madaling basahin at i-update. I-commit ito sa Git repository kasama ng codebase para laging up-to-date.

API Response Format Standards

Bago mag-document, pumili ng standard na response format para sa buong API. Narito ang recommended format:

Success Response:

{
  "success": true,
  "message": "Operation successful",
  "data": { ... }
}

Paginated Response:

{
  "success": true,
  "data": {
    "data": [...],
    "current_page": 1,
    "last_page": 5,
    "per_page": 15,
    "total": 75
  }
}

Error Response:

{
  "success": false,
  "message": "Error description",
  "errors": {
    "field_name": ["Error message 1", "Error message 2"]
  }
}

Ang consistency na ito ay nagpapadali ng frontend development. Ang frontend developer ay alam na kung ang success ay true, nasa data field ang results. Kapag false, nasa message at errors ang details.

Para sa Laravel, i-standardize ito sa isang base controller o response helper:

// app/Http/Controllers/ApiController.php
abstract class ApiController extends Controller
{
    protected function success($data, $message = 'Success', $statusCode = 200)
    {
        return response()->json([
            'success' => true,
            'message' => $message,
            'data' => $data,
        ], $statusCode);
    }

    protected function error($message, $errors = [], $statusCode = 400)
    {
        return response()->json([
            'success' => false,
            'message' => $message,
            'errors' => $errors,
        ], $statusCode);
    }

    protected function paginated($paginator, $message = 'Success')
    {
        return response()->json([
            'success' => true,
            'message' => $message,
            'data' => $paginator,
        ]);
    }
}

Postman Collection Approach

Ang Postman ay isa ring magandang paraan para i-document ang API. Gumawa ng Postman collection at i-export ito bilang JSON file na pwede i-commit sa Git:

Step 1: Buksan ang Postman at gumawa ng bagong collection (halimbawa: "Roxy Store API").

Step 2: I-add ang bawat endpoint bilang request sa collection. Isama ang URL, method, headers, at sample request body.

Step 3: Para sa bawat request, magdagdag ng "Example" responses — isa para sa success, isa para sa error cases.

Step 4: I-export ang collection:点击右键 sa collection → Export → Collection v2.1 → Save as postman-collection.json.

Step 5: I-commit ang postman-collection.json sa Git repository. Ang ibang team members ay pwedeng i-import ito sa kanilang Postman.

Ang Postman collection ay interactive — pwede mong i-run ang mga requests nang hindi nag-le-leave sa Postman. Ito ay mas practical kaysa markdown docs para sa testing.

Practical: Document Your API

Step 1: Gumawa ng API.md file sa root ng Laravel project. I-document ang base URL, authentication method, at ang standard response format.

Step 2: I-list down ang lahat ng existing API endpoints. Para sa bawat endpoint, isama: HTTP method, path, request body/parameters, at response format.

Step 3: Gumawa ngApiController base class na may success() at error() helper methods. I-extend ito ng lahat ng API controllers para sa consistent responses.

Step 4: I-update ang lahat ng existing controllers para gumamit ng bagong response helpers. Palitan ang mga raw response()->json() calls.

Step 5: Gumawa ng Postman collection para sa lahat ng endpoints. I-export at i-commit sa Git.

Step 6: I-share ang documentation sa team. I-explain ang response format at ang mga available endpoints. I-update ang docs kapag may bagong endpoints or changes.
