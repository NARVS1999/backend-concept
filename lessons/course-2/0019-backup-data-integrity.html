Backup & Data Integrity

Matutunan kung paano protektahan ang data mo gamit ang foreign key constraints, cascade strategies, backup strategies, at soft deletes.

Lesson Goal Sa lesson na ito, magagawa mong i-review ang foreign keys ng iyong app, pumili ng tamang cascade strategy (delete, restrict, o set null) para sa bawat relationship, at mag-setup ng basic backup strategy.

Foreign Key Constraints

Ang foreign key constraints ay nag-e-ensure na ang data sa iyong database ay consistent at walang "orphaned" records. Kapag may foreign key, hindi ka puwedeng mag-delete ng parent record na may associated na child records — maliban kung may defined ka na cascade action.

// Sa migration — gumamit ng constrained() para sa foreign keys
Schema::create('posts', function (Blueprint $table) {
    $table->id();
    $table->foreignId('user_id')->constrained()->cascadeOnDelete();
    $table->foreignId('category_id')->constrained()->restrictOnDelete();
    $table->string('title');
    $table->timestamps();
});

// Ang constrained() ay auto-detect ang table at column name:
// foreignId('user_id')->constrained() = foreign key sa users.id
// Ito ay equivalent sa:
$table->foreign('user_id')->references('id')->on('users');

// Kapag walang constraint — pwede kang mag-delete ng user na may posts
// Ito ay nag-ko-cause ng "orphaned" records!

Mga uri ng foreign key constraints:

  • ON DELETE CASCADE — Kapag nag-delete ng parent, auto-delete ang mga child records.
  • ON DELETE RESTRICT — HINDI puwedeng i-delete ang parent kung may child records — mag-throw ng error.
  • ON DELETE SET NULL — Kapag nag-delete ng parent, i-set ang child's foreign key sa NULL.
  • ON DELETE NO ACTION — Walang gagawin — default behavior ng MySQL (hindi nag-a-auto-delete).

Cascade Strategies: Alin ang Gamitin?

Ang pagpili ng cascade strategy ay nakadepende sa business logic — walang "one size fits all" na sagot. Narito ang guidelines:

// CASCADE — gamitin kapag ang child ay WALA nang kwenta kapag wala ang parent
Schema::table('posts', function (Blueprint $table) {
    // Kapag nag-delete ng user, auto-delete ang lahat ng posts niya
    $table->foreign('user_id')->references('id')->on('users')->cascadeOnDelete();
});

// Halimbawa: Comments sa Post
// Kapag nag-delete ng post, auto-delete ang comments — walang silbi ang comments kapag wala ang post
Schema::table('comments', function (Blueprint $table) {
    $table->foreign('post_id')->references('id')->on('posts')->cascadeOnDelete();
});

// RESTRICT — gamitin kapag ayaw mong i-delete ang parent kung may child
Schema::table('orders', function (Blueprint $table) {
    // HINDI puwedeng i-delete ang user kung may orders pa
    $table->foreign('user_id')->references('id')->on('users')->restrictOnDelete();
});

// Halimbawa: Orders sa User
// Hindi puwedeng i-delete ang user kung may outstanding na orders
Schema::table('orders', function (Blueprint $table) {
    $table->foreign('user_id')->references('id')->on('users')->restrictOnDelete();
});

// SET NULL — gamitin kapag ang child ay puwedeng mabuhay nang walang parent
Schema::table('posts', function (Blueprint $table) {
    // Kapag nag-delete ng category, i-set ang category_id sa NULL
    $table->foreign('category_id')->references('id')->on('categories')->nullOnDelete();
});

// Halimbawa: Post sa Category
// Kapag nag-delete ng category, ang post ay mababago ang category sa NULL
// Hindi mawawala ang post — pwede pa rin i-reassign sa ibang category

Decision table para sa cascade strategies:

  • Post → User: CASCADE — kapag nawala ang user, mawawala rin ang posts.
  • Comment → Post: CASCADE — kapag nawala ang post, walang silbi ang comments.
  • Order → User: RESTRICT — hindi puwedeng i-delete ang user kung may orders.
  • Post → Category: SET NULL — pwedeng mabuhay ang post nang walang category.
  • Profile → User: CASCADE — kapag nawala ang user, mawawala rin ang profile.
  • Tag → Post: CASCADE — kapag nawala ang post, mawawala rin ang tag associations.
// Complete example: User deletion cascade strategy
// Sa User model
class User extends Authenticatable
{
    use SoftDeletes;

    public function posts()
    {
        return $this->hasMany(Post::class);
    }

    public function orders()
    {
        return $this->hasMany(Order::class);
    }

    public function profile()
    {
        return $this->hasOne(Profile::class);
    }

    // I-delete ang user nang maayos
    public function deleteUser(): bool
    {
        // Option 1: Cascade (posts deleted, orders blocked)
        // Hindi puwedeng i-delete kung may orders
        if ($this->orders()->exists()) {
            throw new \Exception('Cannot delete user with existing orders.');
        }

        // I-archive ang posts imbis na i-delete
        $this->posts()->update(['user_id' => null]);

        // I-delete ang profile
        $this->profile()->delete();

        // I-soft delete ang user
        return $this->delete();
    }
}

Backup Strategy

Ang backup ay ang iyong insurance policy — kapag may nawala o na-corrupt, pwede mong i-restore ang data. Kahit simpleng backup strategy ay mas wala pa kaysa walang backup.

// Basic MySQL backup command
mysqldump -u root -p database_name > backup_$(date +%Y%m%d_%H%M%S).sql

// Backup specific tables
mysqldump -u root -p database_name users posts > partial_backup.sql

// Backup with compression
mysqldump -u root -p database_name | gzip > backup_$(date +%Y%m%d).sql.gz

// Restore from backup
mysql -u root -p database_name < backup_20240101.sql

// Restore compressed backup
gunzip < backup_20240101.sql.gz | mysql -u root -p database_name

Laravel backup setup:

// Gumamit ng spatie/laravel-backup package
composer require spatie/laravel-backup

// I-configure ang config/backup.php

// Basic backup command
php artisan backup:run

// I-check ang backup status
php artisan backup:check

// I-restore ang backup
php artisan backup:restore

// Automated backup sa cron (daily)
// Sa app/Console/Kernel.php
protected function schedule(Schedule $schedule)
{
    $schedule->command('backup:run')->dailyAt('02:00');
    $schedule->command('backup:clean')->dailyAt('03:00');
}

// Manual backup script (para sa server)
// backup.sh
#!/bin/bash
BACKUP_DIR="/backups/mysql"
DATE=$(date +%Y%m%d_%H%M%S)
mysqldump -u root -p"$DB_PASSWORD" database_name | gzip > "$BACKUP_DIR/backup_$DATE.sql.gz"

# I-delete ang mga backup na mas matagal sa 30 days
find $BACKUP_DIR -name "*.sql.gz" -mtime +30 -delete

Soft Deletes

Ang soft deletes ay hindi talaga nag-de-delete ng records — nag-a-add lang ng deleted_at timestamp. Ito ay nagpo-provide ng data recovery at audit trail.

// Sa migration — gumamit ng softDeletes()
Schema::table('posts', function (Blueprint $table) {
    $table->softDeletes();
});

// Sa model — i-trait ang SoftDeletes
use Illuminate\Database\Eloquent\SoftDeletes;

class Post extends Model
{
    use SoftDeletes;

    // Ang Post::all() ay hindi na isasama ang soft-deleted records
    // Ang Post::withTrashed() ay isasama ang lahat
    // Ang Post::onlyTrashed() ay soft-deleted records lang

    // I-restore ang soft-deleted record
    public function restorePost(int $id): bool
    {
        return Post::withTrashed()->find($id)->restore();
    }

    // I-force delete (talagang ide-delete)
    public function forceDeletePost(int $id): bool
    {
        return Post::withTrashed()->find($id)->forceDelete();
    }
}

// Query sa soft-deleted records
Post::all(); // Hindi isasama ang soft-deleted
Post::withTrashed()->get(); // Isasama ang lahat
Post::onlyTrashed()->get(); // Soft-deleted lang
Post::where('status', 'published')->withTrashed()->get(); // With trashed + filter

// Kapag nag-delete ng user na may posts
// Kung cascade ang foreign key, auto-delete ang posts
// Pero kung soft deletes ang user, hindi auto-delete ang posts
// Kailangan mong i-handle manually

Soft deletes vs hard deletes:

  • Soft deletes — Nag-ko-keep ng data para sa recovery at audit trail. Ang data ay nandoon pa pero "hidden."
  • Hard deletes — Talagang nag-de-delete ng data. Hindi na ma-recover. Mas mabilis at mas malinis.
  • Best practice: Gamitin ang soft deletes para sa important na data (users, posts, orders). Gamitin ang hard deletes para sa transient data (sessions, logs, cache).

Quiz

Summary

  • Ang foreign key constraints ay nag-e-ensure ng data integrity — hindi ka puwedeng mag-delete ng parent record na may associated child records maliban kung may defined cascade action.
  • Ang CASCADE ay auto-delete ang children, RESTRICT ay nag-bblock sa delete, at SET NULL ay nagse-set ng foreign key sa NULL.
  • Laging mag-backup bago mag-migrate sa production — gamitin ang mysqldump o spatie/laravel-backup.
  • Ang soft deletes ay nag-ko-keep ng data para sa recovery — gamitin para sa important na data, i-hard delete para sa transient data.
Interview Angle "How do you handle data deletion in a production Laravel application?" — Gumagamit ako ng soft deletes para sa important na data para may recovery option. I-set ang appropriate cascade strategy: CASCADE para sa dependent data (comments sa posts), RESTRICT para sa critical relationships (orders sa users), SET NULL para sa optional relationships (category sa posts). Laging may backup bago mag-migrate.
