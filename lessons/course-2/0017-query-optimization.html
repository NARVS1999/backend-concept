Query Optimization

Matutunan kung paano i-detect at i-fix ang N+1 problem, gumamit ng EXPLAIN para i-analyze ang queries, at i-optimize ang database performance gamit ang Laravel tools.

Lesson Goal Sa lesson na ito, magagawa mong i-detect ang N+1 queries sa iyong app, i-optimize gamit ang eager loading, at i-analyze ang query performance gamit ang EXPLAIN at DB::listen.

N+1 Problem & Eager Loading

Ang N+1 problem ay isa sa pinaka-common na performance issue sa Laravel apps na gumagamit ng Eloquent. Nangyayari ito kapag nag-fetch ka ng maraming records at saka nag-access ng related data — nag-ko-construct ito ng 1 query para sa parent at N queries pa para sa bawat related record.

// BAD: N+1 problem
$posts = Post::all(); // 1 query

foreach ($posts as $post) {
    echo $post->user->name; // N queries (isa sa bawat post)!
    echo $post->category->name; // Another N queries!
}

// Kung may 100 posts, 1 + 100 + 100 = 201 queries!
// Ang tawag dito ay "N+1 problem"

Eager Loading (with()) ay ang solution — naglo-load ang related data sa iisang query lamang gamit ang JOIN:

// GOOD: Eager loading
$posts = Post::with(['user', 'category'])->get(); // 1 query lang!

foreach ($posts as $post) {
    echo $post->user->name; // Hindi na nag-que-query
    echo $post->category->name; // Hindi na nag-que-query
}

// 2 queries lang total, kahit 100 posts pa

Mga uri ng eager loading:

// Basic eager loading
$posts = Post::with('user')->get();

// Multiple relationships
$posts = Post::with(['user', 'category', 'tags'])->get();

// Nested relationships (user's profile)
$posts = Post::with('user.profile')->get();

// Deep nesting (user's profile's address)
$posts = Post::with('user.profile.address')->get();

// Conditional eager loading
$posts = Post::with(['comments' => function ($query) {
    $query->where('is_approved', true)
          ->orderByDesc('created_at')
          ->limit(5);
}])->get();

// Count relationships (post->comments_count)
$posts = Post::withCount('comments')->get();

// Select specific columns (optimization)
$posts = Post::with('user:id,name,email')->get();

DB::listen para sa Query Logging

Ang DB::listen() ay naglo-log ng lahat ng database queries — makikita mo kung gaano karami at kung gaano kabilis ang bawat query.

// Sa AppServiceProvider.php boot() method
use Illuminate\Support\Facades\DB;
use Illuminate\Support\Facades\Log;

public function boot()
{
    DB::listen(function ($query) {
        // I-log ang queries na mas mabagal sa 100ms
        if ($query->time > 100) {
            Log::warning('Slow query detected', [
                'sql' => $query->sql,
                'time' => $query->time . 'ms',
                'bindings' => $query->bindings,
            ]);
        }

        // Debug mode: i-log ang lahat ng queries
        if (app()->environment('local')) {
            logger()->debug('DB Query', [
                'sql' => $query->sql,
                'time' => $query->time . 'ms',
            ]);
        }
    });
}

// Para sa quick debugging
DB::listen(function ($query) {
    echo "SQL: {$query->sql}\n";
    echo "Time: {$query->time}ms\n";
    echo "Bindings: " . json_encode($query->bindings) . "\n";
});

Pag-count ng queries sa isang request:

// Gumamit ng counter para makita kung gaano karami ang queries
$queries = [];
DB::listen(function ($query) use (&$queries) {
    $queries[] = [
        'sql' => $query->sql,
        'time' => $query->time,
    ];
});

// ... run your code here ...

echo count($queries) . " queries executed\n";
$totalTime = array_sum(array_column($queries, 'time'));
echo "Total time: {$totalTime}ms\n";

EXPLAIN para sa Query Analysis

Ang EXPLAIN ay MySQL command na nagpapakita kung paano nirun ng database ang isang query. Makikita mo kung gumamit ba ng index o full table scan.

// Gamitin ang EXPLAIN sa raw query
$results = DB::select('EXPLAIN SELECT * FROM posts WHERE user_id = ?', [1]);
dd($results);

// Output na tignan:
// type: ALL = full table scan (BAD)
// type: ref = index reference (GOOD)
// type: range = index range scan (OK)
// key: idx_posts_user_id = gamit ang index (GOOD)
// key: NULL = walang index (BAD)
// rows: 1000000 = maraming rows na scan (BAD kung malaki)

Mga EXPLAIN types (from best to worst):

  • system/const — Iisang row lang, pinaka-mabilis.
  • eq_ref — JOIN na nag-gamit ng primary key o unique index.
  • ref — Nag-gamit ng index pero hindi unique.
  • range — Range scan gamit ang index.
  • index — Index full scan (scan ang buong index, hindi table).
  • ALL — Full table scan (pinaka-mabagal — kailangan ng index!).
// Practical: gamitin ang EXPLAIN sa Eloquent
// Una, i-convert ang Eloquent query sa raw SQL
$query = Post::where('user_id', 1)->where('status', 'published');
echo $query->toRawSql(); // Makikita mo ang SQL

// Saka i-run ang EXPLAIN
$results = DB::select(
    'EXPLAIN ' . $query->toRawSql(),
    $query->getBindings()
);
dd($results);

Chunking para sa Large Datasets

Kapag nag-pro-process ka ng malaking halaga ng data (halimbawa: 100,000 rows), wag mong kunin lahat sa iisang query — gumamit ng chunk() para i-break sa mas maliliit na batches.

// BAD: Kunin ang lahat — maaring mag OOM (Out of Memory)
$users = User::all(); // 100,000 rows sa memory!
foreach ($users as $user) {
    // process...
}

// GOOD: Gumamit ng chunk — 1,000 rows per batch lang sa memory
User::chunk(1000, function ($users) {
    foreach ($users as $user) {
        // process...
    }
});

// Alternative: cursor() — lazy loading, hindi naglo-load ng lahat
$users = User::cursor();
foreach ($users as $user) {
    // process one at a time
}

// Gumamit ng cursor kapag nag-iterate lang at hindi nag-queue
// Gumamit ng chunk kapag kailangan mong i-batch ang operations

Practical scenario: listing page optimization

// BEFORE: N+1 problem sa listing page
class PostController extends Controller
{
    public function index()
    {
        $posts = Post::orderByDesc('created_at')->paginate(20);
        // Each page = 1 (posts) + 20 (users) + 20 (categories) = 41 queries!
        return view('posts.index', compact('posts'));
    }
}

// AFTER: Eager loading + selective columns
class PostController extends Controller
{
    public function index()
    {
        $posts = Post::with(['user:id,name,avatar', 'category:id,name'])
            ->select('id', 'title', 'slug', 'user_id', 'category_id', 'created_at')
            ->orderByDesc('created_at')
            ->paginate(20);
        // Total: 3 queries (posts, users, categories) kahit gaano pa karami ang data!
        return view('posts.index', compact('posts'));
    }
}

// BONUS: I-log ang queries para ma-verify ang improvement
class PostController extends Controller
{
    public function index()
    {
        $queryCount = 0;
        DB::listen(function () use (&$queryCount) {
            $queryCount++;
        });

        $posts = Post::with(['user', 'category'])
            ->orderByDesc('created_at')
            ->paginate(20);

        info("Post index: {$queryCount} queries");
        return view('posts.index', compact('posts'));
    }
}

Quiz

Summary

  • Ang N+1 problem ay nag-ko-cause ng maraming queries — isang query para sa parent at N queries para sa related data. I-solve gamit ang with() eager loading.
  • Ang DB::listen() ay naglo-log ng lahat ng queries — gamitin para makita ang slow queries at ang total na bilang ng queries per request.
  • Ang EXPLAIN ay nagpapakita kung paano nirun ng MySQL ang query — tignan ang type at key columns para malaman kung gumamit ng index.
  • Ang chunk() at cursor() ay para sa large datasets — i-break ang processing sa mas maliliit na batches para hindi mag-oom.
Interview Angle "How do you detect and fix the N+1 query problem?" — Gamitin ang DB::listen() para i-log ang queries. Kapag nakita na maraming queries, i-check kung may eager loading. Gamitin ang with() para i-preload ang related data. Gamitin ang EXPLAIN para i-verify na gumagamit ng index.
