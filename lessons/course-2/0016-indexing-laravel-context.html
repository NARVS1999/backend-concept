Indexing sa Konteksto ng Laravel

Matutunan kung paano mag-optimize ng database queries gamit ang tamang indexes at paano ito i-implement sa Laravel migrations.

Lesson Goal Sa lesson na ito, magagawa mong suriin ang mga queries ng iyong app, magdagdag ng appropriate indexes sa Laravel migrations, at maunawaan ang pagkakaiba ng B-tree at hash indexes.

Bakit Kailangan ng Indexes?

Ang index ay parang table of contents ng database. Kapag walang index, ang database ay nag-sa-scan ng buong table (full table scan) para mahanap ang isang row — kung may 1 million rows, 1 million rows ang babasahin. Kapag may index, gagamitin ang index para pumunta direkta sa tamang row — parang gumamit ka ng index sa libro imbis na i-flip ang bawat page.

Mga columns na kailangan ng index:

  • Foreign keys — Ang user_id, post_id, category_id ay madalas gamitin sa JOINs at WHERE clauses.
  • Search columns — Ang email, username, slug na ginagamit sa pag-hahanap.
  • WHERE clause columns — Ang status, type, created_at na madalas naka-filter.
  • ORDER BY columns — Ang columns na ginagamit sa pagination at sorting.
  • Composite columns — Mga combinations na madalas ginagamit magkasama.
// Halimbawa: walang index — mabagal na query
SELECT * FROM posts WHERE user_id = 5 AND status = 'published';
// Full table scan: 1,000,000 rows examined

// Gumamit ng index
ALTER TABLE posts ADD INDEX idx_user_status (user_id, status);
// Index scan: 5 rows examined

B-tree vs Hash Indexes

Ang MySQL ay may dalawang pangunahing uri ng index na gamit sa InnoDB engine:

B-tree Index (default):

  • Ang B-tree ay nagso-sort ng data sa alphabetical/numerical order.
  • Pwede kang mag-range queries: WHERE created_at > '2024-01-01'.
  • Pwede ring gamitin sa equality: WHERE id = 5.
  • Ito ang pinaka-common at versatile na index type.
  • Pwede kang mag-ORDER BY gamit ang indexed column — hindi na kailangan ng separate sort.

Hash Index:

  • Ang hash index ay ginagamit lang sa equality comparisons (= o IN()).
  • Hindi puwedeng gamitin sa range queries — hindi supported ang >, <, BETWEEN.
  • Mas mabilis kaysa B-tree sa exact lookups pero limited ang gamit.
  • Pwede lang i-define sa MEMORY storage engine o sa NDB Cluster.
  • Para sa InnoDB, ginagamit ang adaptive hash index — auto-managed ng MySQL.
// B-tree index (default) — pwede sa range at equality
Schema::table('posts', function (Blueprint $table) {
    $table->index('created_at'); // B-tree by default
});

// Hindi mo kailangan mag-specify ng type para sa B-tree
// Pero kung gusto mong i-explicit:
Schema::table('posts', function (Blueprint $table) {
    $table->index('created_at', 'idx_posts_created', 'btree');
});

Rule of thumb: Gamitin ang B-tree (default) sa 99% ng cases. Ang hash index ay rarely needed — pabayaan mo na lang ang MySQL para sa adaptive hash indexing.

Paano Mag-Add ng Index sa Laravel Migrations

Laravel ay nagpo-provide ng malinis na syntax para sa indexes sa migrations:

// Simple index — isang column
Schema::table('posts', function (Blueprint $table) {
    $table->index('status');
});

// Composite index — dalawa o higit pang columns
Schema::table('posts', function (Blueprint $table) {
    $table->index(['user_id', 'status']);
});

// Unique index — bawal ang duplicates
Schema::table('users', function (Blueprint $table) {
    $table->unique('email');
});

// Index with custom name
Schema::table('posts', function (Blueprint $table) {
    $table->index('slug', 'idx_posts_slug');
});

// Full-text index — para sa search
Schema::table('posts', function (Blueprint $table) {
    $table->fullText(['title', 'body']);
});

// Prefix index — i-index lang ang unang N characters
Schema::table('posts', function (Blueprint $table) {
    $table->index('title', 'idx_posts_title_prefix', 'btree')->prefix(10);
});

Composite index ordering:

  • I-order ang columns mula sa most selective (maraming unique values) hanggang least selective.
  • Ang (user_id, status) ay efficient para sa WHERE user_id = 5 AND status = 'published'.
  • Pero ang same index ay hindi efficient para sa WHERE status = 'published' lang — hindi masusunod ang order.
  • Gumawa ng separate index kung may queries na gumagamit lang ng status.
// Composite index example
Schema::table('orders', function (Blueprint $table) {
    // For queries like: WHERE user_id = ? AND status = ? ORDER BY created_at DESC
    $table->index(['user_id', 'status', 'created_at'], 'idx_orders_user_status_date');
});

// Eloquent query that uses this index efficiently
Order::where('user_id', $userId)
    ->where('status', 'processing')
    ->orderByDesc('created_at')
    ->paginate(20);

Practical: Review & Optimize Tables

Para malaman kung aling columns ang kailangan ng index, suriin mo ang mga queries na ginagamit mo:

// Step 1: I-log ang queries para makita kung ano ang mabagal
// Sa AppServiceProvider.php
public function boot()
{
    DB::listen(function ($query) {
        if ($query->time > 100) { // > 100ms
            Log::warning("Slow query: {$query->sql}", [
                'time' => $query->time . 'ms',
                'bindings' => $query->bindings,
            ]);
        }
    });
}

// Step 2: I-check ang existing indexes
Schema::getColumnListing('posts'); // List lahat ng columns
Schema::getColumns('posts'); // Detailed info
Schema::getIndexes('posts'); // List lahat ng indexes

// Step 3: Gumawa ng migration para mag-add ng indexes
Schema::table('posts', function (Blueprint $table) {
    $table->index('user_id');
    $table->index('status');
    $table->index(['status', 'created_at']);
    $table->unique('slug');
});

// Step 4: I-check ang query performance gamit ang EXPLAIN
DB::select('EXPLAIN SELECT * FROM posts WHERE user_id = ? AND status = ?', [1, 'published']);

Migration naming convention para sa indexes:

// Para sa mga bagong tables — idagdag sa create migration
Schema::create('posts', function (Blueprint $table) {
    $table->id();
    $table->foreignId('user_id')->constrained();
    $table->string('title');
    $table->text('body')->nullable();
    $table->enum('status', ['draft', 'published'])->default('draft');
    $table->timestamps();

    $table->index('user_id');
    $table->index('status');
    $table->index(['status', 'created_at']);
});

// Para sa existing tables — gumawa ng separate migration
Schema::table('posts', function (Blueprint $table) {
    $table->index('status');
});

// I-rollback: tanggalin ang index
Schema::table('posts', function (Blueprint $table) {
    $table->dropIndex('posts_status_index');
});

Common mistakes:

  • Over-indexing — Wag mong i-index ang lahat ng columns. Bawat index ay nagpapabagal sa INSERT/UPDATE/DELETE dahil kailangan i-update ang index.
  • Redundant indexes — Ang index na (user_id, status) ay sapat na; huwag mo nang gumawa ng separate (user_id) index.
  • Ignoring composite indexes — Ang composite index ay mas efficient kaysa sa maraming single-column indexes.
  • Not checking existing indexes — Bago ka mag-add ng index, i-check mo muna kung meron na.

Quiz

Summary

  • Ang indexes ay pino-point ang database sa tamang rows — hindi na kailangan ng full table scan.
  • Ang B-tree (default) ay versatile — pwede sa equality at range queries. Ang hash ay limited sa equality lang.
  • I-index ang mga foreign keys, search columns, WHERE clause columns, at ORDER BY columns.
  • Mag-composite index para sa queries na gumagamit ng maraming columns magkasama — i-order mula sa most selective.
  • Huwag mag-over-index — bawat index ay nagpapabagal sa writes.
Interview Angle "How would you optimize a slow Laravel query?" — Una, i-check ang query gamit ang EXPLAIN. Kung walang index, mag-add gamit ang migration. Gamitin ang composite index para sa multi-column WHERE clauses. I-log ang slow queries gamit ang DB::listen para makita ang mga problema.
