Environment Configuration

Paano ba i-manage ang mga settings at secrets nang tama sa Laravel at Next.js para sa iba't ibang environment?

Lesson Goal Sa lesson na ito, magagawa mong i-set up nang tama ang environment variables sa Laravel at Next.js, maihiwalay ang dev/staging/production configurations, at maiwasan ang hardcoded secrets sa codebase.

Bakit Mahalaga ang Environment Variables?

Ang environment variables ay mga values na nagbabago depende sa kung saan tumatakbo ang application. Ang database credentials, API keys, at URLs ay hindi dapat naka-hardcode sa codebase dahil:

Security: Kapag naka-commit ang secrets sa Git repository, maa-access ito ng sinuman. Ito ay security vulnerability.

Flexibility: Ang development URL ay iba sa production URL. Ang local database credentials ay iba sa production database credentials.

Portability: Hindi mo kailangang baguhin ang code kapag nag-deploy sa ibang environment. Ang environment variables ang mag-a-adjust.

Kaya naman, ang best practice ay ilagay ang lahat ng configurable values sa .env files at huwag kailanman i-commit ang .env sa Git.

.env Management sa Laravel

Ang Laravel ay may built-in na support para sa environment variables gamit ang .env file. Narito ang karaniwang structure:

# .env (Laravel)
APP_NAME="Roxy Store"
APP_ENV=local
APP_KEY=base64:xxxxx
APP_URL=http://localhost:8000

DB_CONNECTION=mysql
DB_HOST=127.0.0.1
DB_PORT=3306
DB_DATABASE=roxy_store
DB_USERNAME=root
DB_PASSWORD=secret

CACHE_DRIVER=file
SESSION_DRIVER=file
QUEUE_CONNECTION=sync

NEXTJS_URL=http://localhost:3000
FRONTEND_URL=http://localhost:3000

JWT_SECRET=your-jwt-secret-here

Ang .env.example file ay committed sa Git bilang template. Ang actual na .env ay nasa .gitignore. Kapag nag-setup ang bagong developer, kopyahin lang nila ang .env.example papuntang .env at i-fill ang mga values.

Ang pag-access sa environment variables sa Laravel ay gamit ang env() helper o ang config() function. Gumamit ng config files para i-wrap ang environment variables:

// config/services.php
return [
    'nextjs' => [
        'url' => env('NEXTJS_URL', 'http://localhost:3000'),
    ],

    'jwt' => [
        'secret' => env('JWT_SECRET'),
    ],
];

// Usage sa code:
$nextUrl = config('services.nextjs.url');

Ang pattern na ito ay nagbibigay ng default value at nag-e-ensure na ang configuration ay organized sa iisang lugar.

.env Management sa Next.js

Ang Next.js ay may sariling paraan ng environment variable handling. Gumamit ng .env.local para sa local development variables:

# .env.local (Next.js)
NEXT_PUBLIC_API_URL=http://localhost:8000/api
NEXTAUTH_URL=http://localhost:3000
NEXTAUTH_SECRET=your-nextauth-secret

# Hindi lalabas sa browser (server-side only)
DATABASE_URL=mysql://root:secret@localhost:3306/roxy_store

# Lalabas sa browser (client-side)
NEXT_PUBLIC_API_URL=http://localhost:8000/api

Ang NEXT_PUBLIC_ prefix ay nagpo-protocol na ang variable ay accessible sa browser. Ang mga walang prefix ay server-side lang — hindi ito makikita ng client code, kaya safe para sa sensitive data.

I-access ang variables sa Next.js:

// Server-side (API routes, getServerSideProps)
const apiUrl = process.env.NEXT_PUBLIC_API_URL;

// Client-side (React components)
const apiUrl = process.env.NEXT_PUBLIC_API_URL;

// Sa next.config.js (build-time)
module.exports = {
  env: {
    API_URL: process.env.NEXT_PUBLIC_API_URL,
  },
};

Separating Dev, Staging, and Production Configs

Ang pinaka-common na approach ay gumamit ng iba't ibang .env files para sa iba't ibang environment:

Laravel: Ang APP_ENV value ang nagdedetermine kung aling environment ang gamit. Ang config:cache ay nag-c-cached ng configuration para sa performance.

# Development
APP_ENV=local
APP_DEBUG=true
DB_HOST=127.0.0.1

# Production
APP_ENV=production
APP_DEBUG=false
DB_HOST=production-db-host.com

Next.js: Ang .env.development, .env.staging, at .env.production ay auto-loaded depende sa next build o next dev command.

# .env.development
NEXT_PUBLIC_API_URL=http://localhost:8000/api

# .env.production
NEXT_PUBLIC_API_URL=https://api.roxy.com/api

Para sa deployment platforms tulad ng Vercel, i-set ang environment variables sa dashboard nila. Ang Vercel ay auto-detect ng NEXT_PUBLIC_ variables at i-i-inject habang build.

Practical: Set Up Environment Variables

Sundin ang mga ito para sa iyong Laravel + Next.js project:

Step 1: Sa Laravel, gumawa ng .env file mula sa .env.example. I-set ang lahat ng DB credentials, app URL, at NEXTJS_URL.

Step 2: Gumawa ng config files sa config/ directory para i-wrap ang environment variables. Halimbawa: config/frontend.php para sa Next.js URL.

Step 3: Sa Next.js, gumawa ng .env.local. I-set ang NEXT_PUBLIC_API_URL pointing sa Laravel API.

Step 4: Siguraduhin na ang .env at .env.local ay nasa .gitignore. I-commit lang ang .env.example at .env.local.example.

Step 5: Gumawa ng .env.production para sa Next.js production settings. I-set ang production API URL.

Step 6: I-test ang configuration. Gumawa ng simple API call mula sa Next.js papunta sa Laravel. Siguraduhin na ang URL ay galing sa environment variable, hindi hardcoded.

Summary

  • Huwag kailanman i-commit ang .env files sa Git — gumamit lang ng .env.example bilang template
  • Sa Next.js, ang NEXT_PUBLIC_ prefix ay nagpo-protocol na accessible sa browser; walang prefix ay server-side lang
  • Gumamit ng config files sa Laravel para i-wrap ang env variables — mas organized at may default values
  • I-separate ang dev/staging/production configs gamit ang iba't ibang env files o deployment platform settings
