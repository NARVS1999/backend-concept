Secrets Management

Paano ba i-manage ang mga sensitibong impormasyon tulad ng database credentials, API keys, at encryption keys sa production environment?

Lesson Goal Sa lesson na ito, magagawa mong i-setup ang secrets management para sa Laravel at Next.js, maiwasan ang pag-leak ng credentials sa Git, at malaman ang best practices para sa production environment variables.

Bakit Mahalaga ang Secrets Management?

Ang "secrets" ay ang mga sensitibong data na hindi dapat ma-expose: database passwords, API keys, encryption keys, at third-party service credentials. Kapag na-leak ang mga ito — especially sa Git — maaaring magamit ng malicious actors para ma-access ang sistema mo, magnakaw ng data, o mag-cause ng damage sa production.

Common scenarios na nag-cause ng leaks:

  • Naka-commit ang .env file sa public Git repository — ang lahat ay nakaka-access sa database credentials
  • Naka-hardcode ang API key sa source code — kahit sino na may access sa repo ay makikita ito
  • Na-share ang screenshot na may visible credentials — common sa Discord at Slack
  • Na-expose ang environment variables sa deployment logs — minsan ang CI/CD ay nag-lo-log ng sensitive data

Ang consequences ay serious: data breach, financial loss, legal liability, at reputational damage. Kahit ang mga experienced developers ay nagkakamali — ang importante ay ang system na ginagamit mo ay may safeguards para maiwasan ang leaks.

Laravel .env Best Practices

Ang Laravel ay gumagamit ng .env file para sa environment variables. Narito ang mga rules na dapat sundin:

Rule 1: Hindi dapat i-commit ang .env file sa Git.

# .gitignore - dapat nandito ang .env
.env
.env.backup
.env.production
.env.local

Rule 2: Gumawa ng .env.example file na committed sa Git.

# .env.example - committed sa Git
# Ang mga values dito ay placeholders, hindi actual credentials

APP_NAME=Roxy
APP_ENV=local
APP_KEY=
APP_DEBUG=true
APP_URL=http://localhost:8000

DB_CONNECTION=mysql
DB_HOST=127.0.0.1
DB_PORT=3306
DB_DATABASE=roxy
DB_USERNAME=root
DB_PASSWORD=

CACHE_DRIVER=file
QUEUE_CONNECTION=sync

# Third-party API keys
STRIPE_KEY=
STRIPE_SECRET=
MAIL_MAILER=smtp
MAIL_HOST=
MAIL_PORT=587
MAIL_USERNAME=
MAIL_PASSWORD=

Rule 3: Gamitin ang Laravel Vault para sa highly sensitive secrets.

# Laravel Vault - encrypted secrets storage
# I-install ang vault
composer require laravel/vault
php artisan vault:install

# I-add ang sensitive secrets
php artisan vault:set stripe_secret sk_live_xxxxx
php artisan vault:set mail_password xxxxx

# Sa code, i-access gamit ang helper
$stripeSecret = vault('stripe_secret');
$mailPassword = vault('mail_password');

Ang Laravel Vault ay nag-e-encrypt ng secrets at ini-store ang decryption key sa separate location (hindi sa .env). Ito ay para sa mga secrets na hindi dapat ma-access kahit na ma-compro ang .env file.

Rule 4: I-separate ang configuration per environment.

# Sa deployment server, gumawa ng production .env
# Ito ay hindi naka-commit sa Git

APP_ENV=production
APP_DEBUG=false
APP_URL=https://roxy.com
APP_KEY=base64:xxxxx  # generated key

DB_HOST=127.0.0.1
DB_DATABASE=roxy_production
DB_USERNAME=roxy_user
DB_PASSWORD=secure_password_here

CACHE_DRIVER=redis
QUEUE_CONNECTION=redis

Environment Variables sa Next.js

Ang Next.js ay may dalawang uri ng environment variables:

PUBLIC variables — accessible sa client-side code (browser). I-prefixed ng NEXT_PUBLIC_:

# .env.local (hindi committed sa Git)
NEXT_PUBLIC_API_URL=https://api.roxy.com
NEXT_PUBLIC_STRIPE_KEY=pk_live_xxxxx
NEXT_PUBLIC_APP_NAME=Roxy

Server-only variables — accessible lang sa server-side code (API routes, Server Components, middleware):

# Server-only (walang NEXT_PUBLIC_ prefix)
DATABASE_URL=postgresql://user:pass@host:5432/db
STRIPE_SECRET=sk_live_xxxxx
JWT_SECRET=xxxxx

Deployment-specific configuration:

# Vercel - environment variables sa dashboard
# Settings → Environment Variables
# I-set ang variable per environment: Production, Preview, Development

# Sa code, i-access gamit:
const apiUrl = process.env.NEXT_PUBLIC_API_URL;  // client-safe
const dbUrl = process.env.DATABASE_URL;  // server-only

Warning: Ang NEXT_PUBLIC_ variables ay visible sa browser — huwag mong ilagay ang sensitive data dito. Ang API keys na naka-expose sa client-side ay makikita ng kahit sino gamit ang browser developer tools.

Git Security: Preventing Leaks

Beyond sa .env management, may iba pang paraan para maiwasan ang secret leaks:

1. Pre-commit hooks: I-scan ang staged files bago i-commit. Gamitin ang git-secrets o truffleHog:

# Install git-secrets
brew install git-secrets  # macOS
# o
apt install git-secrets  # Ubuntu

# I-setup sa repo
git secrets --install
git secrets --register-aws  # AWS patterns

# Mag-a-automate na ito kapag may na-commit na secret
# Mag-error kapag may AWS key na na-detect

2. GitHub secret scanning: I-enable ang secret scanning sa GitHub repository settings. Mag-a-auto-detect ng known secrets at mag-no-notify kapag may na-push.

3. .gitignore comprehensive list:

# .gitignore - dapat kumpleto
.env
.env.*
!.env.example
*.key
*.pem
*.p12
*.pfx
*.secret
*.credentials
node_modules/
vendor/
storage/*.key

4. Audit existing commits: Kung suspect ka na may na-leak na secret dati, i-scan ang buong Git history:

# Gamitin ang truffleHog para i-scan ang Git history
pip install trufflehog
trufflehog git file://./your-repo --only-verified

Para sa Laravel, i-revoke agad ang compromised keys at gumawa ng bago. I-rotate ang database credentials at API keys kapag na-detect ang leak.

Practical: Set Up Production Secrets

Step 1: I-review ang lahat ng secrets sa .env file mo. I-list down ang bawat variable at i-categorize: database credentials, API keys, encryption keys, at service configurations.

Step 2: I-setup ang .gitignore para siguraduhin na hindi ma-commit ang .env file. I-commit ang .env.example na may placeholder values.

Step 3: Sa production server, i-create ang .env file gamit ang actual credentials. I-set ang APP_ENV=production at APP_DEBUG=false.

Step 4: I-setup ang Vercel environment variables: i-add ang lahat ng required variables sa dashboard, i-separate ang production at preview environments.

Step 5: I-install ang git-secrets at i-setup ang pre-commit hooks sa local machine. I-test na nag-e-error kapag may AWS key pattern na na-detect.

Step 6: I-rotate ang lahat ng existing credentials: bagong database password, bagong API keys, bagong encryption key. I-deploy ang bagong credentials sa production.

Step 7: I-document ang secrets management process sa team. I-explain kung aling secrets ang nasa saan at paano mag-add ng bago nang hindi nag-le-leak.
