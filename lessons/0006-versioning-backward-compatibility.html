Phase 2: API Design — Lesson 2 of 4

Versioning & Backward Compatibility

Paano i-evolve ang API mo nang hindi sinisira ang existing clients.

Lesson Goal Maunawaan ang iba't ibang versioning strategies at kung paano mag-handle ng breaking changes nang hindi naaapektuhan ang mga lumang clients.

Bakit Kailangan ng Versioning?

Kapag may nagbago sa API mo (new fields, renamed fields, removed endpoints), ang existing clients (mobile apps, other services) ay pwedeng masira. Solusyon: i-version ang API para parehong gumana ang luma at bagong versions.

Versioning Strategies

1. URL Versioning

GET /api/v1/users
GET /api/v2/users
  • Pros: Simple at explicit
  • Cons: "Pollutes" ang URL space

2. Header Versioning

Accept: application/vnd.myapp.v1+json
Accept: application/vnd.myapp.v2+json
  • Pros: Mas malinis ang URL
  • Cons: Mas mahirap i-test (kailangan mag-set ng headers)

Breaking vs Non-breaking Changes

  • Non-breaking — Magdagdag ng bagong field sa response, magdagdag ng bagong endpoint
  • Breaking — Mag-rename o mag-remove ng field, magpalit ng data type, magpalit ng endpoint URL
Tip Kung may existing mobile app na tumatawag sa API mo at kailangan mong magdagdag ng required field, gawin mo munang optional ang field (non-breaking). Pag handa na ang mobile app, saka mo gawing required sa susunod na version.

Quiz

Summary

  • Versioning protects existing clients from breaking changes
  • URL versioning at header versioning ang most common strategies
  • Adding fields = non-breaking; removing/renaming fields = breaking
  • I-deprecate muna, huwag biglang tanggalin
Interview Angle "May existing mobile app na tumatawag sa API mo. Paano ka magdadagdag ng required field nang hindi nakaka-break sa kanila?"
