Phase 2: API Design — Lesson 3 of 4

Pagination, Filtering, Sorting

Paano mag-handle ng malalaking datasets sa API nang hindi nabobomba ang server o client.

Lesson Goal Maunawaan ang offset vs cursor-based pagination at kung kelan gagamitin ang bawat isa.

Bakit Kailangan ng Pagination?

Kung ang isang endpoint ay puwedeng magreturn ng libo-libo o milyon-milyong records, kailangan nating i-break ito sa mas maliliit na pages. Hindi pwedeng i-load lahat nang sabay — mauubos ang memory ng server at babagal ang client.

Offset Pagination

GET /users?offset=0&limit=20
GET /users?offset=20&limit=20
GET /users?page=1&per_page=20
  • Simple at madaling i-implement
  • Problema: unstable kapag may bagong records na na-insert (pwedeng ma-duplicate o ma-skip ang records)
  • Mabagal sa malaking offset (kailangan pa ring i-scan ng database ang naunang rows)

Cursor-based Pagination

GET /users?cursor=eyJsYXN0X2lkIjogMTAwfQ==&limit=20
  • Gumagamit ng cursor (usually encoded ID or timestamp) para ituro kung saan magsisimula
  • Stable — kahit may new records na na-insert, hindi magbabago ang results
  • Mas mabilis sa malaking datasets (direktang WHERE id > cursor)
  • Hindi pwedeng mag-jump sa arbitrary page number
Remember Cursor-based pagination ang preferred pag infinite scroll feeds (Facebook, Twitter, Instagram). Offset pagination okay para sa admin panels na may "Go to page 5" feature.

Filtering at Sorting

GET /users?role=admin&status=active&sort=created_at&order=desc
  • Gamit ang query parameters
  • Consistent naming convention
  • I-limit ang allowed sort fields para iwasan ang abuse

I-implement ang parehong offset at cursor pagination sa isang listing endpoint. I-benchmark performance sa malaking dataset.
